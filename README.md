# イベント受付（SvelteKit 学習用サンプル）

イベントの申込から当日の受付までを、SvelteKit のサーバー側機能だけで組んだ小さなアプリです。
`load` でのデータ取得、`form actions` での更新、コンポーネント分割、型の持ち方を一通り確認するために作りました。

## 起動

```bash
npm install
npm run dev
```

ローカルでは Node 標準の `node:sqlite` を使い、初回起動時に `data/app.db` を作成して
デモ用のイベントと参加者を投入します。DB ファイルを消せば次回起動時に作り直されます。

```bash
npm run check              # svelte-check による型チェック
npm run build              # 本番ビルド（.vercel/output を生成）
npm run db:reset -- --yes  # テーブルを作り直してデモデータを入れ直す
```

`db:reset` は破壊的な操作なので、`--yes` が無ければ対象を表示して何もしません。
`DATABASE_URL` が設定されていれば Neon を、無ければローカルの SQLite を対象にします。

環境変数 `DATABASE_URL`（または `POSTGRES_URL`）が設定されている場合は、SQLite ではなく
Neon（PostgreSQL）に接続します。

## 画面

| パス | 内容 |
| --- | --- |
| `/` | 開催予定のイベント一覧。受付中とそれ以外を分けて表示する |
| `/events/[slug]` | イベント詳細と参加申込フォーム |
| `/events/[slug]/attendees` | 運営向けの参加者管理。受付・受付取消・キャンセル |

## 設計の意図

**入力チェックはサーバーを正とする。** `validation.ts` の関数をサーバーの action とクライアントの
`use:enhance` の両方から呼び、ルールを 1 か所に閉じています。クライアント側は送信前の早出しだけを担当します。

**入力値の保持先はフォーム要素。** コンポーネントに入力値の写しを持たず、失敗時はサーバーが返した値を
`value` として描き戻します。JavaScript を切った状態でも入力が消えません。

**定員と重複の判定は 1 文にまとめる。** 「受付中か」「空きがあるか」「申込済みでないか」の判定と挿入を
`INSERT ... SELECT ... ON CONFLICT` の 1 文で行い、別々に問い合わせてから挿入することによる定員超過を避けています。
キャンセル済みの行に同じアドレスで申し込み直した場合だけ、その行を復活させます。

**定員チェックはイベント単位で直列化する。** 「数えてから書く」処理は PostgreSQL の既定の
READ COMMITTED では同時実行で両方通ってしまいます。`querySerialized` がイベントの slug をキーに
`pg_advisory_xact_lock` を取ってから実行するので、同じイベントへの同時申込だけが待ち合わせます。
SQLite 側は単一の書き込みロックで元から直列化されるため、同じ SQL をそのまま実行します。

SERIALIZABLE 分離レベルに上げて直列化の失敗（40001）を再試行する方法も試しましたが、
競合が連鎖すると再試行で吸収しきれず、実測で 20 並列中 13 件がエラーになり席も売れ残りました
（下記「確認済みの動作」）。アボートさせて数えるより、待たせるほうが素直でした。

**データアクセスは `repository.ts` に閉じる。** ルート側は SQL も行の形も知りません。
`db/` が「`$1` 形式のプレースホルダで問い合わせる」ことだけを公開するインターフェースになっているので、
SQLite と PostgreSQL で SQL は 1 種類しか書いていません。方言差（プレースホルダの記法、主キーの採番、
日時型の返り方）は `db/` の中に閉じています。

**キャンセルは行を消さない。** `status` を変えるだけにして、残席の集計から外します。

## 確認済みの動作

ブラウザ（一覧・詳細・参加者管理の表示、申込、受付）と、`use:enhance` を通さない POST で
確認した結果です。いずれも開発サーバー + SQLite での実測です。

なお開発ビルドでは SvelteKit の CSRF チェック（`__SVELTEKIT_CSRF_CHECK_ORIGIN__`）が無効なため、
`Origin` ヘッダ無しの POST でも action まで到達します。本番ビルドでは有効で、`Origin` が一致しない
POST は 403 `Cross-site POST form submissions are forbidden` になります。実ブラウザは `Origin` を
送るので JavaScript 無効時も通常どおり動作しますが、curl で本番を叩く場合は `Origin` を付ける必要があります。

| 操作 | 結果 |
| --- | --- |
| 申込（正常） | 200。登録され、残席が減り、完了メッセージを表示 |
| 未入力・メール形式不正 | 400。フィールドごとのエラー文と入力値の差し戻し |
| 同じメールアドレスで再申込 | 409「すでに登録されています」 |
| 受付 | 200。受付済みに変わり、受付時刻を表示 |
| 受付済みをもう一度受付 | 409「受付できる状態ではありません」 |
| 受付取消 / 取消の二重実行 | 200 / 409「受付済みではありません」 |
| キャンセル / 二重実行 | 200（残席が戻る）/ 409「すでにキャンセル済みです」 |
| 存在しない ID・別イベントの ID | 404「参加者が見つかりません」 |
| ID が空・数値でない | 400「特定できませんでした」 |
| 受付終了イベントへの申込 | 409「申込を受け付けていません」 |
| キャンセル後に同じアドレスで再申込 | 200。同じ行が復活し、重複行は作られない |

入力中にエラーが解消されること（名前を入力するとそのフィールドのエラーが消える）もブラウザで確認しています。

`npm run check` は 0 エラー 0 警告、`npm run build` は成功します。

### PostgreSQL 側の確認

ローカルに立てた PostgreSQL 16 に対して、`schema.ts` の DDL / 初期データと、`repository.ts` から
取り出した申込登録の SQL をそのまま実行して確認しました（Neon の HTTP ドライバ自体は未確認で、
確認したのは SQL とロックの挙動です）。

- スキーマ作成（`GENERATED ALWAYS AS IDENTITY` / `TIMESTAMPTZ` / `CHECK` / `UNIQUE`）
- 初期データの投入と、2 回目に何もしないこと
- `timestamptz` が `Date` で返ること（`toIsoString` で ISO 文字列に揃える必要があるため）
- 申込の登録 / 重複の拒否 / 受付終了イベントの拒否 / キャンセル後の同一行の復活 / 定員到達後の拒否

### 同時申込

残り席数と並列数を変えて実測しました。いずれも定員超過はありません。

| 条件 | 結果 |
| --- | --- |
| 残り 1 席 / 20 並列 | 200 が 1 件、409 が 19 件。定員ちょうど（85ms） |
| 残り 8 席 / 20 並列 | 200 が 8 件、409 が 12 件。定員ちょうど（98ms） |
| 残り 15 席 / 30 並列 | 200 が 15 件、409 が 15 件。定員ちょうど（141ms） |

同じ条件を SERIALIZABLE + 再試行（3 回）で試したときは、残り 8 席 / 20 並列で
**500 が 13 件、登録は 7 件（1 席売れ残り）** でした。この結果を受けてアドバイザリロック方式に変えています。

SQLite 側でも残り 1 席 / 10 並列で 200 が 1 件、409 が 9 件、定員ちょうどに収まることを確認しています。

### 本番（Vercel + Neon）での確認

デプロイ済みの公開URLに対して、実際のブラウザと curl で確認しました。

| 操作 | 結果 |
| --- | --- |
| 一覧 / 詳細 / 参加者管理の表示 | 200 |
| 存在しない slug | 404 |
| 申込（正常） | 200 |
| 重複 / 入力不備 / 受付終了イベント | 409 / 400 / 409 |
| 受付 / 受付済みの再受付 / 受付取消 | 200 / 409 / 200 |
| 存在しない参加者 ID | 404 |

**同時申込**: 定員 12・申込 1 件（残り 11 席）の状態に 20 並列で申し込んだところ、
**200 が 11 件、409 が 9 件**、最終的に 12 / 12 の満席ちょうどに収まりました。
500 は 0 件、売れ残りもありません。サーバーレス関数は複数インスタンスに分かれて実行されるため、
これは単一プロセスのローカル検証より厳しい条件での確認になります。

これで `querySerialized` のアドバイザリロックが Neon の HTTP ドライバ経由でも機能することと、
`sql.transaction()` が単一トランザクションとして扱われることが実地で確認できました。

確認後、検証で作成した 12 件のテスト行は削除し、初期データの 3 件に戻してあります。

## デプロイ

Vercel 向けに `@sveltejs/adapter-vercel`（Node ランタイム）を使います。

```bash
npx vercel@latest deploy --prod
```

実行時には Neon の接続文字列が必要です。Vercel Marketplace の Neon 連携を追加すると、
Neon のアカウントとプロジェクトが作成され、`DATABASE_URL` がプロジェクトに自動で注入されます
（接続文字列を手でコピーする必要はありません）。環境変数は新しいデプロイから反映されます。

接続文字列が無いまま Vercel 上で動かすと、`db/index.ts` が設定漏れとして明示的に停止します。
`node:sqlite` は書き込み可能なファイルシステムを必要とするため、サーバーレス環境では使えません。

Neon のリージョンは、関数の実行リージョンに合わせてください。レスポンスヘッダの
`x-vercel-id: <edge>::<function region>::<id>` で確認できます（このデプロイは `iad1` = US East）。
